# **План тестирования продукта «Помощник судьи»**

Версия: 1.0  
 Объект: Flutter-приложение (Android 8.0+, iOS 14.0+), backend FastAPI, PostgreSQL, Redis, S3-совместимое хранилище, Google OAuth, push/email, OS-share, PDF/CSV/PNG.  
 Основание: ТЗ «Приложение “Помощник судьи”», ИОП-ИТ-24/1 от 15.10.2026.

---

## 1\. Цели тестирования

1. Подтвердить выполнение всех функциональных требований актуального ТЗ.  
2. Подтвердить выполнение NFR: производительность, надёжность, безопасность, совместимость, удобство, хранение, поддерживаемость, локализация, правовые ограничения.  
3. Обеспечить высокое покрытие критических модулей: авторизация, права доступа, список соревнований, соревнования, приглашения, участники, оценки, завершение, результаты, графики, PDF, уведомления, офлайн-синхронизация, удаление и автоудаление соревнований.  
4. Проверить корректность формул, транзакционность, конкурентную безопасность, отсутствие утечек оценок до завершения.  
5. Подготовить доказательства для приёмки: отчёты, метрики, UAT, матрицу трассируемости.

## 2\. Границы тестирования

### Входит

* Все функциональные требования актуального ТЗ.  
* Все NFR ТЗ.  
* API, UI, интеграции, отчёты, экспорт, уведомления, офлайн.  
* Безопасность, права доступа, транзакционность, конкурентность.  
* UAT с не менее 10 судьями.  
* Статический анализ, code review, проверка зависимостей и секретов.

### Не входит

* Маркетинг, поддержка после гарантийного периода, доработки вне согласованного объёма.  
* Обучение как отдельная услуга, кроме проверки сценария «обучение ≤20 минут».  
* Реальные персональные данные; используются синтетические тестовые данные.  
* Передача прав администратора (не предусмотрена ТЗ).

## 3\. Ключевые правила актуального ТЗ, влияющие на тесты

Ниже зафиксированы правила, по которым строятся тест-кейсы. Любое изменение — через change request с обновлением тест-плана.

### 3.1 Приглашения

* Отправка новых приглашений — только до старта.  
* После старта все необработанные приглашения истекают и не могут быть приняты; отклонение также недоступно.  
* Администратор не получает уведомление «принял/отказался» по истёкшим приглашениям.  
* Отдельное уведомление об истечении приглашения ТЗ не предусматривает.

### 3.2 Удаление соревнования

* До старта — администратор может удалить соревнование.  
* После старта и до завершения — удаление запрещено.  
* После завершения — администратор может удалить соревнование.  
* Автоудаление через 1 год после завершения — автоматическое, без участия пользователя.  
* Удаление — soft-delete с сохранением аудита; связанные приглашения аннулируются; при ручном удалении все судьи получают уведомление.  
* Автоудаление уведомлением не сопровождается (уведомление по ТЗ предусмотрено для ручного удаления).  
* Удалённые соревнования не отображаются в списке; API возвращает 404/410.

### 3.3 Список соревнований

* Меню со списком всех соревнований, где пользователь является судьёй (включая администратора).  
* В списке: название, даты, место, статус (не начато / начато / завершено).  
* Удалённые соревнования не отображаются.  
* Соревнования, где пользователь не судья, не отображаются.  
* Порядок по умолчанию — по дате (по согласованию с заказчиком); требование о сортировке в ТЗ не зафиксировано.

### 3.4 Прочие правила

* Оценки — целые 0…10; итог судьи \= артистизм \+ техника (0…20).  
* Завершение — когда каждый участник имеет хотя бы одну оценку; не оценившие судьи не включаются в средние.  
* Округление — 2 знака, banker’s rounding.  
* Уникальность (judge\_id, participant\_id, competition\_id).  
* Офлайн-конфликт — LWW по клиентскому времени, проигравшая запись в аудит.  
* Google OAuth — feature flag.  
* 18+ чекбокс при регистрации.  
* Дубли ФИО — нормализация: trim, схлопывание пробелов, нижний регистр, «ё»=«е»; дефис и апостроф значимы.  
* Аудит 6 месяцев; RELEASE-логи без ПД; DEBUG только dev/staging.

## 4\. Подход и уровни тестирования

Риск-ориентированный подход. Приоритет:

1. Права доступа и авторизация.  
2. Приглашения и их истечение после старта.  
3. Удаление и автоудаление соревнований.  
4. Список соревнований и статусы.  
5. Оценки и завершение.  
6. Расчёты результатов.  
7. Транзакционность и сохранность данных.  
8. Безопасность.  
9. PDF/графики/экспорт.  
10. Уведомления и офлайн.  
11. NFR и UAT.

| Уровень | Что проверяется | Ответственный |
| :---- | :---- | :---- |
| Статический анализ | SAST, линтеры, secret scanning, dependency scan | DevOps \+ QA |
| Code review | Логика, права, транзакции, обработка ошибок | Разработчики \+ QA |
| Unit | Формулы, валидации, утилиты, права | Разработчики |
| Property-based | Формулы, граничные значения, инварианты | QA \+ разработчики |
| Contract | Flutter ↔ FastAPI ↔ БД ↔ S3 ↔ email/push | QA |
| Integration/API | FastAPI, PostgreSQL, Redis, S3, OAuth | QA |
| UI/E2E | Критические сценарии Flutter | QA |
| System | Сквозные сценарии соревнования | QA |
| Performance/Load | p95, нагрузка | QA \+ DevOps |
| Security | OWASP Top 10, TLS, bcrypt, rate limit, доступ | QA \+ DevOps |
| Compatibility | Android/iOS, минимальное железо | QA |
| Accessibility | WCAG 2.1 AA | QA |
| Localization | Русский, дата, часовой пояс | QA |
| UAT | 10 судей, SUS, сценарии | PM \+ QA |
| Regression | Критические E2E \+ NFR smoke | QA \+ CI |

Виды тестирования: функциональное, негативное, граничные значения, права доступа, интеграционное, E2E, регрессионное, smoke, производительность, нагрузка, стресс, надёжность, восстановление, безопасность, совместимость, доступность, локализация, UAT, офлайн, отчёты, exploratory, mutation, TTL/job-тесты (автоудаление).

## 7\. Тест-кейсы по модулям

Формат: ID \| Название \| Предусловия \| Шаги \| Ожидаемый результат \| Приоритет \| Тип.

### 7.0 Как читать тест-кейс (обязательная легенда)

**Столбцы.** *Предусловия* — что должно быть готово ДО первого шага (если не выполнено — сначала выполните их). *Шаги* — пронумерованные действия; выполняйте по порядку, одно действие = один шаг. *Ожидаемый результат* — проверяйте буквально: каждый пункт из результата должен наблюдаться на экране/в ответе. Если хотя бы один пункт не совпал — это Failed с комментарием, какой именно пункт.

**Роли в кейсах:**

| Обозначение | Значение |
| :---- | :---- |
| «Админ» / «Администратор» | Судья, создавший соревнование (он же судья этого соревнования) |
| «Судья A» / «Судья B» | Разные зарегистрированные судьи, участники одного соревнования |
| «Чужой судья» | Зарегистрированный судья, НЕ входящий в данное соревнование |
| «Неаутентифицированный» | Запрос без токена (curl/Postman без Authorization) |

**Базовые синтетические тестовые данные** (заменяются актуальными при появлении стенда; реальные ПД использовать запрещено):

| Параметр | Значение |
| :---- | :---- |
| Судья 1 (админ) | judge1@example.com / Judge1-Pass! (подтверждён, 18+) |
| Судья 2 | judge2@example.com / Judge2-Pass! (подтверждён, 18+) |
| Судья 3 (без подтверждения) | judge3@example.com / Judge3-Pass! |
| Тестовое соревнование | «Тестовое соревнование №1», 05.12.2026–07.12.2026, место «Тестовый зал» |
| Участник-эталон | Иванов Иван Иванович, Взрослые, комментарий пустой |

**Правила записи результатов (TestY):** статус Passed/Failed/Blocked + комментарий; для Failed обязательно: окружение, шаг воспроизведения, фактический результат, ожидаемый; скриншот приложить. Кейсы с пометкой «серая зона 3.5.N» выполняются строго по допущению из раздела 3.5.

## 11. Автоматизация и CI/CD

Smoke: вход, список, создание, приглашение, участник, старт (истечение приглашений), оценка, завершение, результаты, PDF, удаление.  
 Regression: критические E2E \+ права \+ уведомления \+ экспорт \+ офлайн \+ TTL-автоудаление \+ NFR smoke.  
 Автоматизация: unit, API (pytest), UI (integration\_test), performance (k6), security (ZAP/SAST), contract, property-based, TTL-job-тесты.  
 CI quality gates: линтеры, SAST, secret scan, dependency scan, unit, API, coverage ≥80% критических, smoke E2E.  
 Сборка каждые 2 недели с недели 5; демо в конце недель 6, 9, 12; RC — неделя 11\.

## 12\. Критерии входа и выхода

* Список соревнований отображает поля и статусы; удалённые не отображаются.  
* Трассируемость полная; регрессия зелёная.

## 15\. Дефекты и метрики

Severity: Blocker, Critical, Major, Minor, Trivial.  
 Приоритет: P0–P3.  
 Workflow: New → Triage → In Progress → Fixed → Retest → Closed/Reopened.  
 Релиз блокируется при Blocker/Critical; Major — только с согласованным workaround.

Метрики: выполнено/пройдено/упало/заблокировано; дефекты по severity/модулям; defect leakage; coverage ≥80%; p95; SUS; 90% без обучения; ≤3 действий; ≤20 минут; доступность; RPO/RTO.

## 18\. Критерии приёмки

1. Все функциональные требования актуального ТЗ выполнены.  
2. NFR измерены и подтверждены.  
3. UAT с не менее 10 судьями проведён.  
4. Нет критических и блокирующих багов.  
5. PDF соответствует согласованному шаблону.  
6. Данные не теряются при сбое сети — проверено сценарием с отключением сети.  
7. LWW-конфликт двух устройств подтверждён; дублей нет.  
8. Покрытие критических модулей тестами ≥80%.  
9. Трассируемость полная; регрессия зелёная.  
10. Security-проверки без Critical/High.  
11. Feature flag Google OAuth проверен в обоих состояниях.  
12. Удаление администратора самим собой запрещено.  
13. После старта все необработанные приглашения истекают и не могут быть приняты или отклонены; админ не получает уведомление «принял/отказался».  
14. Удаление соревнования: разрешено до старта и после завершения; запрещено между стартом и завершением; автоудаление через 1 год после завершения работает.  
15. Список соревнований отображает название, даты, место, статус; удалённые и чужие не отображаются.
