# Онбординг команды: полное погружение в проект за 2 часа

Для кого: каждый участник команды «Помощник судьи» перед защитой.
Цель: через 2 часа вы можете своими словами объяснить, что за продукт, как он тестируется,
где живут тест-кейсы, как устроены автотесты и CI/CD, и умеете на своём ноутбуке:
поднять TestY, запустить приложение, прогнать автотесты, сделать push и деплой одной командой.

**Перед стартом проверьте (2 мин):**
- Docker Desktop запущен (значок в трее, `docker --version` отвечает).
- Репозиторий склонирован: `git clone <url-репозитория>` и вы в его корне.
- Установлен Python 3.11+ (`python --version`).

**Легенда работы с документом:** каждый блок — время + конкретные действия (✋ «руками»)
и вопросы самопроверки. Если действие не получается — раздел «Если что-то не работает» в конце.

## Блок 3 (30–60 мин). TestY: система управления тестированием (TMS)

TestY — это наш аналог testIT: склад тест-кейсов, планов, прогонов и результатов.
Всё уже развёрнуто и наполнено; вам нужно научиться в нём работать.

✋ Запуск (один раз, ~3–5 минут):
```bat
cd testy
docker compose up -d
```
- Интерфейс: **http://127.0.0.1** (frontend)
- Backend API: http://127.0.0.1:8001, Swagger: http://127.0.0.1:8001/api/v2/swagger/
- Встроенная документация TestY: http://127.0.0.1/docs/
- Админ: логин `admin`, пароль `password` (из testy/.env)
- Пользователи команды: `irina`, `darya`, `timur` — пароль `Testy-2026!` (смените при первом входе)

✋ Практика по шагам (делайте под своей учёткой):
1. Войдите → откройте проект **«Помощник судьи»** → вкладка **Test Suites**: увидите дерево
   7.1…7.12 (функциональные), 9.x (NFR), раздел 8 (права), раздел 10 (UAT). Всего 275 кейсов.
2. Откройте сьют 7.6 → найдите кейс FIN-03 (оценка вне диапазона). Изучите поля: Name, Setup,
   Steps (ожидаемый результат у каждого шага), метки (P-приоритет, тип `Boundary`).
3. Вкладка **Test Plans**: откройте «Функциональное тестирование — распределение задач» —
   196 кейсов с исполнителями из xlsx. Найдите СВОИ кейсы по фильтру исполнителя.
4. Откройте план «Smoke-регрессия (демо)» → нажмите **создать Test Run** → прогоните 2–3 кейса:
   проставьте один **Passed**, один **Failed** (приложите скриншот как вложение) —
   по инструкции из [docs/testy_руководство_тестировщика.md](testy_руководство_тестировщика.md), разделы 4–5.
5. Посмотрите статистику плана (диаграмма прогресса) — это то, что попадает в итоговый отчёт.

Статусы результата: **Passed / Failed / Blocked** (+ In Progress). Failed ≠ «приложение сломано
навсегда»: по Failed заводится дефект (POM1-xxx в YouGile), после исправления — Re-test.

Вопросы самопроверки:
- Чем Test Run отличается от Test Plan? (План — набор кейсов для выполнения; прогон — выполнение плана на конкретной сборке с результатами.)
- Что делать, если кейс упал? (Зафиксировать Failed + вложение → завести дефект по шаблону → после фикса Re-test.)

## Блок 5 (85–110 мин). CI/CD: push → тесты → образ → деплой одной командой

Это главный флоу защиты. Схема: **push в GitHub → Actions: lint → тесты (2 версии Python,
coverage ≥ 80%) → smoke → сборка Docker-образа → smoke в контейнере → скан Trivy →
публикация образа в GHCR → локально: одна команда поднимает готовый образ с миграциями.**

### 5.1. Настройка GitHub (если ещё не сделано, ~10 мин)

1. Создайте пустой репозиторий на GitHub (например, `judge-helper-project`).
2. В терминале корня проекта:
```bat
git remote add origin https://github.com/<владелец>/judge-helper-project.git
git add -A
git commit -m "Проект «Помощник судьи»: приложение, тесты, TestY, CI/CD"
git push -u origin master
```
3. Откройте вкладку **Actions** в GitHub — пайплайн запустится сам. Дождитесь зелёных
   джоб: `Линтер (ruff)` → `Тесты (3.11/3.12)` → `Smoke-проверка` → `Образ`.
4. **Важно**: в джобе `Образ` раскройте шаг «Публикация образа в GHCR» — там записано точное
   имя образа. Для нашего репозитория это: **`ghcr.io/xnairix/judge_helper/judge-helper:latest`**
   (владелец в адресе GHCR приводится к нижнему регистру). Запишите его себе.
5. Сделайте пакет публичным: GitHub → ваш профиль → **Packages** → judge-helper →
   **Package settings → Change visibility → Public** (иначе docker pull не сможет скачать без логина).
6. В джобе `Тесты` откройте **Summary** — артефакт `test-reports` (coverage.xml + report.xml)
   можно скачать: это те самые отчёты, что упоминаем в блоке «CI/CD» защиты.

### 5.2. Локальный деплой одной командой (~5 мин)

✋ Один раз: в корне репозитория создайте файл `.env` (рядом с docker-compose.deploy.yml):
```bat
echo JUDGE_IMAGE=ghcr.io/xnairix/judge_helper/judge-helper:latest> .env
echo APP_PORT=8300>> .env
```
Второй порт нужен, потому что Windows резервирует диапазоны портов (проверка:
`netsh interface ipv4 show excludedportrange protocol=tcp`) — на этом ноутбуке 8000 и 8080
попадают в зарезервированный диапазон 7922–8221, поэтому берём 8300.

✋ Теперь каждая сборка после push запускается ОДНОЙ командой:
```bat
docker compose -f docker-compose.deploy.yml up -d
```
Что произойдёт: compose скачает свежий `latest`-образ из GHCR (`pull_policy: always`),
поднимет контейнер на http://127.0.0.1:8300. **Миграции применятся автоматически при старте** —
приложение выполняет `create_all` + миграции ранних версий (см. [app/src/judge_helper/main.py](../app/src/judge_helper/main.py),
`create_app`). Данные хранятся в volume `judge_data` и переживают пересоздание контейнера.
Проверка: `curl http://127.0.0.1:8300/health` → `{"status":"ok"}`.
Файл `.env` не коммитится — это локальные настройки (секреты).

### 5.3. Сценарий «упавший тест» (10 мин) — репетируем поиск ошибки в логах

✋ Сделайте на ветке:
```bat
git checkout -b demo/broken-test
```
Откройте любой тест, например [app/tests/test_scores_api.py](../app/tests/test_scores_api.py),
и сломайте одно ожидание (например, замените `assert r.status_code == 422` на `== 500`):
```bat
git add -A && git commit -m "demo: broken test" && git push -u origin demo/broken-test
```
1. В Actions откройте красный прогон → джоба `Тесты` → найдите в логе **traceback pytest**:
   имя теста, `assert` с фактическим/ожидаемым значением, файл и строку.
   Линтер упал? Тогда ошибка видна в выводе `ruff check` построчно.
2. «Исправьте» локально, проверьте точечно: `pytest tests/test_scores_api.py -v`,
   закоммитьте, запушьте → пайплайн снова зелёный.
3. Удалите ветку: `git push origin --delete demo/broken-test` и вернитесь на `master`.

Вопросы самопроверки:
- Что делает пайплайн при падении теста? (Дальнейшие джобы не выполняются: образ не соберётся и не опубликуется — fail fast.)
- Где смотреть причину падения? (Лог упавшей джобы в Actions; артефакты test-reports в Summary.)

## Если что-то не работает

| Симптом | Причина / решение |
| :-- | :--- |
| `docker compose up` ругается на Docker | Docker Desktop не запущен — откройте и дождитесь «Engine running» |
| TestY не поднимается на Windows | Известные проблемы и решения: [docs/testy_руководство.md](testy_руководство.md), раздел 4.3 (autocrlf, кириллические пути) |
| `docker compose -f docker-compose.deploy.yml up` просит JUDGE_IMAGE | Не создан `.env` — см. блок 5.2 |
| Образ не скачивается (`denied`) | Пакет в GHCR приватный — сделайте Public (блок 5.1, шаг 5) или выполните `docker login ghcr.io` |
| Порт 8000 занят | Либо остановите старый контейнер (`docker compose -f app/docker-compose.yml down`), либо задайте в `.env` строку `APP_PORT=8001` |
| CI красный, но локально всё зелёное | Проверьте, что запушены все файлы (`git status`); посмотрите лог упавшей джобы — обычно ruff (форматирование) или шрифты в тестах PDF |
| 403 при ручных проверках прав | Это ожидаемо: матрица прав (раздел 8 плана) блокирует чужие действия — так и должно быть |
