# TestY TMS — установка и руководство по работе для проекта «Помощник судьи»

Версия документа: 1.0
Инструмент: [TestY TMS 2.2.1](https://gitlab-pub.yadro.com/testy/testy/) (open source, AGPLv3, разработка KNS Group LLC / YADRO)
Стек TestY: Django (backend) + React (frontend) + PostgreSQL + Redis, поставка через Docker Compose.

---

## 1. Зачем нам TestY

План тестирования (раздел 5) требует инструмент test management. TestY закрывает потребности проекта:

* тест-кейсы, сгруппированные в наборы (suites) с неограниченной вложенностью;
* тест-планы, тестовые прогоны (runs) и результаты выполнения (в т.ч. загрузка результатов автотестов);
* метки (labels) и пользовательские атрибуты для срезов отчётности (приоритеты P0–P3, типы тестов);
* история изменений тест-кейсов, комментарии, вложения;
* статистика и диаграммы прогресса планов;
* публичный REST API + Swagger для интеграций и автоматизации;
* встроенные плагины: импорт из TestRail, импорт отчётов Allure, экспорт планов;
* интерфейс локализован на русский язык; документация доступна прямо в системе по адресу `/docs/`.

## 2. Ключевые понятия (глоссарий TestY)

| Термин | Значение |
| :-- | :-- |
| Project | Контейнер всей тестовой модели продукта. У нас один проект — «Помощник судьи». |
| Test Suite | Набор для хранения тест-кейсов, объединённых по признаку; наборы вкладываются друг в друга. |
| Test Case | Тестовый сценарий проверки. Бывает **сценарным** (общий ожидаемый результат) и **пошаговым** (ожидаемый результат у каждого шага). Поля: Name, Setup (предусловия), Scenario/Steps, Expected, Teardown, Estimate, Labels, Description. |
| Test Plan | Набор тестов, выбранных для выполнения (например, smoke-регрессия спринта). |
| Test Run | Прогон группы тестов плана на определённой версии сборки или стадии тестирования. |
| Test | Связка «тест-кейс в конкретном плане» с его результатами. |
| Test Result | Результат выполнения теста в прогоне (статус, комментарий, вложения, по шагам — статус каждого шага). |
| Label | Метка кейса для фильтрации и срезов (у нас: приоритет и тип теста). |
| Custom Attribute | Дополнительное поле объекта, настроенное на уровне проекта. |

## 4. Установка с нуля (Windows 10/11)

### 4.1 Требования

* Docker Desktop с поддержкой WSL2 (проверка: `docker --version`, `docker compose version`);
* OpenSSL в WSL2 — только для production-развёртывания (self-signed сертификаты);
* git.

### 4.2 Шаги (development-режим, как выполнено у нас)

```bat
:: 1. Клонируем репозиторий БЕЗ преобразования переводов строк (важно, см. 4.3)
git clone -c core.autocrlf=input https://gitlab-pub.yadro.com/testy/testy.git testy
cd testy

:: 2. Конфигурация из шаблона
copy .env.template .env
::    для dev-режима значений по умолчанию достаточно (VITE_APP_API_ROOT=http://127.0.0.1);
::    при желании задайте свои SUPERUSER_USERNAME / SUPERUSER_PASSWORD

:: 3. Проверить, что entrypoint.sh с LF-переводами строк (иначе контейнер testy упадёт)
::    (после клона с core.autocrlf=input — уже LF)

:: 4. Собрать образы (первый раз ~10–20 минут)
docker compose -f docker-compose-dev.yml build

:: 5. Поднять стек
docker compose -f docker-compose-dev.yml up -d

:: 6. Дождаться здоровья контейнеров и открыть http://127.0.0.1
docker ps --format "table {{.Names}}\t{{.Status}}"
```

Ожидаемый состав контейнеров: `nginx`, `testy-frontend`, `testy`, `testy_celery`, `testy_pgbouncer`, `testy_db`, `testy_redis`, `notifications`.

Production-развёртывание отличается: `nginx/make_ssl.sh`, правка `.env` (SECRET_KEY, VITE_APP_API_ROOT с FQDN/IP, HTTPS) и `docker compose up`. Подробности — README репозитория и `http://<host>/docs/` → «Инсталляция».

### 4.3 Известные проблемы (Windows)

| Проблема | Причина / лечение |
| :-- | :-- |
| Контейнер `testy` падает с `entrypoint.sh: no such file or directory` | Git/IDE преобразовали LF→CRLF при клонировании. Лечится клоном с `core.autocrlf=input` либо возвратом LF в `backend/testy/scripts/entrypoint.sh`. |
| `Login Failed` при верных credentials | Открывается URL, отличный от `VITE_APP_API_ROOT` в `.env`. В dev заходим строго на `http://127.0.0.1` (без порта и без https). |
| Долгая первая сборка | Норма: собираются Python- и Node-образы; повторные сборки идут из кэша. |

### 4.4 Развёртывание на сервере с конкретным IP (куда указывать адрес)

Когда TestY переносится с локальной машины на сервер (например, `192.168.1.50` или FQDN `testy.mycompany.ru`), адрес указывается в **четырёх местах файла `testy/.env`** (все они закомментированы подсказками прямо в `.env`):

| Переменная в `testy/.env` | Что означает | Пример значения |
| :-- | :-- | :-- |
| `VITE_APP_API_ROOT` | **Главный адрес системы**: по нему собирается фронтенд и по нему нужно открывать UI в браузере. | `https://192.168.1.50` |
| `ALLOWED_HOSTS` | Хосты, которые Django принимает (JSON-список). | `'["192.168.1.50", "localhost"]'` |
| `CSRF_TRUSTED_ORIGINS` | Origins, с которых разрешены POST/PUT/PATCH (иначе — 403 на логине). | `'["https://192.168.1.50"]'` |
| `HOST_NAME` | Имя сервера nginx (server_name). По умолчанию `_` — любой. | `192.168.1.50` |

Порядок действий:

```bat
cd testy
:: 1. Правим .env: VITE_APP_API_ROOT, ALLOWED_HOSTS, CSRF_TRUSTED_ORIGINS, HOST_NAME (см. таблицу)
:: 2. Пересобираем и перезапускаем (фронтенд «зашивает» адрес при сборке!)
docker compose -f docker-compose-dev.yml up -d --build
:: 3. Открываем в браузере СТРОГО тот же адрес, что в VITE_APP_API_ROOT
```

Нюансы:

* **HTTP или HTTPS.** В dev-режиме nginx отдаёт только 80-й порт — используйте `http://<IP>`. HTTPS (443) включается в production-развёртывании (`docker-compose.yml` + `nginx/make_ssl.sh` или обычные сертификаты), тогда адрес в `VITE_APP_API_ROOT` — `https://<IP/FQDN>`.
* **Порты.** Публикуемые порты заданы в `docker-compose(-dev).yml`: nginx — `80:80` (и `443:443` в prod), backend — `8001:8000`, БД — `5435/5436`, Redis — `6380`. Для доступа команды достаточно открыть в файрволе порт nginx (80/443); остальные порты наружу можно закрыть.
* **Скрипты импорта** при переносе: `python tools\testy_import\import_test_cases.py --base-url http://<IP>:8001 …` (или `https://<IP>`, если backend за nginx проксируется).
* Если браузер выдаёт «Login Failed» при верных данных — вы открыли адрес, отличный от `VITE_APP_API_ROOT`.

## 5. Повседневная эксплуатация

```bat
cd testy
docker compose -f docker-compose-dev.yml up -d      :: старт
docker compose -f docker-compose-dev.yml stop       :: остановка (данные сохраняются)
docker compose -f docker-compose-dev.yml down       :: остановка и удаление контейнеров (тома с БД остаются)
docker logs -f testy                                :: логи backend
docker logs -f testy_celery                         :: логи фоновых задач
```

* Данные БД лежат в Docker-томах/каталоге `VOLUMES_PATH` (`./volumes` по умолчанию): `pg-data`, `redis_data`, `media`.
* **Сохранность данных при перезапуске: ничего не пропадает.** Все кейсы, планы, результаты, пользователи и вложения хранятся в PostgreSQL на диске (`testy/volumes/pg-data`), контейнеры — stateless. Команды `stop` / `up -d` / `restart` / `down` (без флагов) полностью сохраняют данные — после старта всё будет на месте, заново импортировать ничего не нужно.
* **Когда данные действительно пропадут:** `docker compose down -v` (флаг `-v` удаляет тома), удаление каталога `testy/volumes/`, пересоздание томов вручную. Также не храните `VOLUMES_PATH` внутри удаляемых путей (см. советы README для production). На этот случай — делайте бэкапы (ниже) и помните: полный набор кейсов всегда можно восстановить скриптами из `tools/testy_import/`, а вот результаты прогонов восстановит только бэкап БД.
* Обновление версии TestY: `docker compose down` (без `-v`!) → бэкап БД и `backend/testy/media` → `git pull` → проверка `.env` → `docker compose up -d --build`. Процедура описана в README («Upgrade»).

### Бэкапы

```bat
:: холодный бэкап БД
docker compose -f docker-compose-dev.yml stop testy_db
xcopy /e /i volumes\pg-data backups\pg-data-<дата>
docker compose -f docker-compose-dev.yml start testy_db

:: горячий бэкап БД
docker compose exec -T testy_db sh -c "pg_dump -U postgres -d postgres -Fc" > backups\db.dump

:: вложения
xcopy /e /i backend\testy\media backups\media-<дата>
```

## 7. Работа в интерфейсе: быстрый старт

### 7.1 Вход и дашборд

1. Открыть `http://127.0.0.1`, войти (`admin` / ваш пароль).
2. Дашборд показывает карточки проектов со счётчиками Test Suites / Test Cases / Test Plans / Tests. Кнопка **+ PROJECT** создаёт проект.

### 7.2 Вкладки проекта

* **Overview** — сводка, прогресс выполнения планов, статусы;
* **Parameters** — параметры для параметризованных тестов;
* **Labels** — метки проекта (создание/правка цветов);
* **Statuses** — статусы результатов (настраиваемый набор и порядок);
* **Custom Attributes** — пользовательские поля кейсов/планов/тестов (text, list, json);
* **Settings** — настройки проекта (редактируемость результатов и лимит правки);
* **Access Management** — участники и роли;
* **Integrations** — подключения (Allure, TestRail-импорт и др.).

### 7.3 Test Suites & Cases

1. Слева иконка «Test Suites & Cases».
2. Дерево наборов слева, список кейсов справа (переключение дерево/таблица).
3. **+ TEST SUITE** — новый набор (можно дочерним к выбранному).
4. **+ TEST CASE** — новый кейс:
   * сценарный: Scenario + общий Expected;
   * пошаговый: флажок Steps, у каждого шага свой сценарий и ожидаемый результат;
   * Setup — предусловия, Teardown — действия после, Estimate — трудоёмкость, Labels — метки.
5. Все текстовые поля поддерживают Markdown и вложения. Каждое сохранение кейса создаёт версию: история правок доступна в правой панели кейса (выпадающий список версий, сравнение, восстановление).
6. Массовые операции над кейсами: перенос между наборами, копирование, простановка/снятие меток, добавление в планы, архивирование.

### 7.4 Test Plans & Results

1. Иконка «Test Plans & Results» слева → **+ TEST PLAN**: имя, даты (started_at/due_date), описание, выбор кейсов (фильтром по наборам/меткам или перечислением).
2. Кейсы, добавленные в план, становятся **тестами** плана.
3. Внутри плана: вкладка **Tests** (назначение исполнителей, метки, статусы) и **Test Runs** — прогоны:
   * создать run на версию сборки/стадию;
   * в run фиксировать **результаты** каждого теста: статус (Passed/Failed/Blocked и настроенные в Statuses), комментарий, вложения; для пошаговых кейсов — статус каждого шага;
   * результат можно исправить в течение окна, заданного в Settings проекта (по умолчанию 1 час).
4. Статистика плана: диаграммы по статусам, прогресс, срезы по меткам — вкладка Overview плана и `/testplans/<id>/statistics/` в API.

### 7.5 Результаты автотестов

Результаты автоматических прогонов загружаются через интеграции (плагин Allure) или REST API (`/api/v2/results/`), после чего видны в тех же планах/прогонах и статистике.

## 8. Наша структура тест-кейсов и трассируемость

Соответствие «план тестирования → TestY»:

| План тестирования | TestY |
| :-- | :-- |
| Раздел 7.x (таблицы кейсов) | Набор `7.x <название>` внутри «Раздел 7 — Тест-кейсы по модулям» |
| Раздел 9.x (NFR: таблицы 9.1/9.2/9.4/9.5/9.7 и списки 9.6/9.8/9.9) | Наборы `9.x <название>` внутри «Раздел 9 — NFR-тесты» |
| Раздел 8 (матрица прав доступа) | Корень «Раздел 8 — Матрица прав доступа», кейсы AM-01…AM-06 |
| Раздел 10 (UAT и приёмка) | Корень «Раздел 10 — UAT и приёмка», кейсы UAT-01…UAT-12 |
| docs/распределение_задач.xlsx (исполнители, дедлайны) | План «Функциональное тестирование — распределение задач (декабрь 2026)»: assignee у каждого теста |

| Колонка «Приоритет» | Метка P0/P1/P2/P3 (цветная) |
| Колонка «Тип» | Метка типа (Functional, Security, …) |

Матрица прав доступа (раздел 8 плана) и негативные сценарии покрыты метками `Access`/`Security` — фильтр по метке даёт готовый срез для прогона.

**Как добавлять новые кейсы:** правим таблицы в `docs/план_тестирования.md` → запускаем `python tools/testy_import/import_test_cases.py` → скрипт доcоздаст только новые наборы/кейсы (идемпотентен: существующие пары «набор+имя» пропускает).

## 10. REST API

* Swagger UI: `http://127.0.0.1:8001/api/v2/swagger/` (Redoc: `/redoc/`).
* Аутентификация — JWT: `POST /api/token/` (логин/пароль) → `access`/`refresh`; продление `POST /api/token/refresh/`.
* Основные эндпоинты (префикс `/api/v2/`): `projects/`, `suites/`, `cases/`, `labels/`, `custom-attributes/`, `testplans/`, `tests/`, `testrun/`, `results/`, `statuses/`, `parameters/`, `attachments/`, `notifications/`, `integrations/`, статистика `testplans/<id>/statistics/`.

Пример (PowerShell):

```powershell
$t = (Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8001/api/token/ -ContentType 'application/json' -Body '{"username":"admin","password":"password"}').access
Invoke-RestMethod -Uri 'http://127.0.0.1:8001/api/v2/cases/?project=1' -Headers @{Authorization="Bearer $t"}
```

## 11. Рекомендуемый процесс работы команды

1. **QA-lead** ведёт наборы и кейсы (раздел 8 настоящего документа), метки и планы; изменения правил ТЗ → change request → правка плана тестирования → доимпорт скриптом.
2. **Каждую сборку** (каждые 2 недели с недели 5) создаётся Test Run в плане регрессии; smoke-прогон обязателен (план «Smoke-регрессия»).
3. **Результаты** фиксируются в run: Passed/Failed/Blocked + комментарий и вложения (скриншоты, логи); дефекты заводятся по workflow плана (раздел 15) и связываются с кейсом через комментарий/ID.
4. **Отчётность**: Overview плана и срезы по меткам P0/P1 — еженедельно; к приёмке — матрица «требование → кейс → результат» выгружается из TestY (фильтры + экспорт планов плагином test-plan-exporter).
5. **Автотесты** (pytest/API, Flutter integration_test, k6): результаты загружаются в планы через API/Allure-плагин, чтобы статистика плана объединяла ручные и автоматические прогоны.
6. **UAT (неделя 10–11)**: отдельные run'ы на судей-UAT с фиксацией SUS-наблюдений комментариями.

## 12. Troubleshooting

| Симптом | Действие |
| :-- | :-- |
| `http://127.0.0.1` не открывается | `docker ps` — все ли контейнеры Up; `docker logs nginx`, `docker logs testy`; убедиться, что Docker Desktop запущен. |
| Контейнер `testy_db` unhealthy | Первый запуск инициализирует БД ~1–2 минуты; подождать. Иначе `docker logs testy_db`. |
| `entrypoint.sh: no such file or directory` | CRLF-проблема: вернуть LF в `backend/testy/scripts/entrypoint.sh` и пересоздать контейнер (`up -d --force-recreate testy`). |
| Забыт пароль администратора | `docker compose exec testy python manage.py changepassword admin` (или сбросить том БД для dev-стенда). |
| Браузер показывает устаревшие данные после апгрейда | Очистить local storage браузера. |
