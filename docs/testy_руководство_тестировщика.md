## 2. Интерфейс за две минуты

После входа вы на **Dashboard** — плитки проектов. Вам нужен проект **«Помощник судьи»**. У плитки три кнопки:

* **Overview** — сводка и статистика проекта;
* **Test Suites & Cases** — библиотека всех тест-кейсов (как они устроены, читательский раздел);
* **Test Plans & Results** — **ваш основной раздел**: планы, ваши задачи, результаты.

Слева — панель навигации (сворачивается), сверху — поиск, уведомления (колокольчик) и профиль.

Два главных понятия, которые нужны каждый день:

* **Test Case (кейс)** — сценарий проверки: предусловия (Setup), шаги (Scenario), ожидаемый результат (Expected). Кейсы менять не нужно — они уже готовы.
* **Test (тест)** — кейс, добавленный в тест-план и назначенный конкретному человеку. У теста есть **статус** (Untested, Passed, Failed, Blocked…) и **результаты** выполнения. Вот с тестами вы и работаете.

## 3. Где мои задачи

Ваши кейсы уже распределены (по `docs/распределение_задач.xlsx`): у каждого из вас ~65 тестов в плане **«Функциональное тестирование — распределение задач (декабрь 2026)»**.

Как увидеть только свои:

1. Слева — иконка **Test Plans & Results**.
2. В левой панели выберите план «Функциональное тестирование — распределение задач (декабрь 2026)».
3. Над таблицей тестов справа нажмите **FILTER**.
4. В открывшейся панели найдите сегмент **Assignee** и выберите себя (irina / darya / timur).
5. Нажмите на «гаечный ключ»/сохранение фильтра — сохраните его под именем «Мои задачи», чтобы не настраивать каждый раз. Сохранённые фильтры доступны в любой момент.

В таблице полезные колонки: **ID** и **Name** (например, `AUTH-01 Регистрация по email`), **Labels** (P0 — критичный, P1 — важный), **Last Status** (текущий статус), **Assignee** (исполнитель). Колонку **+ Result** запомните — это быстрый способ записать результат.

> Совет: за дедлайнами своих задач удобно следить в исходном файле `docs/распределение_задач.xlsx` (доски 01–12 = наборы 7.1–7.12) — в TestY дедлайн общий на план.

## 4. Главный рабочий цикл: тест → проверка → результат

Для каждого назначенного вам теста:

**Шаг 1. Откройте тест.** Клик по названию теста — справа откроется панель с содержимым кейса: Setup (предусловия), Scenario (шаги), Expected (ожидаемый результат). Внизу панели — история результатов и комментарии.

**Шаг 2. Выполните проверку на тестируемой сборке приложения** строго по шагам. Предусловия (Setup) должны быть выполнены до начала: например, «соревнование не начато», «аккаунт создан». Если шаги нельзя выполнить как написано (например, в сборке нет такого экрана) — это тоже находка, см. Blocked/Failed.

**Шаг 3. Запишите результат:**

1. Нажмите **ADD RESULT** (кнопка на панели теста; то же самое делает колонка **+ Result** в таблице).
2. В форме заполните:
   * **Status** — итоговый статус (см. таблицу ниже);
   * **Comment** — что вы сделали и что увидели (для Failed — обязательно, см. раздел 5);
   * **Attachments** — скриншот, лог, запись экрана (перетащите файл в поле).
3. Нажмите **CREATE**.

Статус обновится в колонке **Last Status**, и он попадёт в статистику плана (кольцевые диаграммы на Overview плана — прогресс команды виден всем).

### Какой статус ставить

| Статус | Когда ставить |
| :-- | :-- |
| **Passed** | Все шаги прошли, фактический результат совпал с Expected. |
| **Failed** | Получили не то, что в Expected (баг), либо по ходу шагов возникла ошибка. Комментарий и скриншот обязательны. |
| **Blocked** | Проверка невозможна по внешней причине: нет тестовых данных, стенд недоступен, блокируется другим багом. В комментарии — что именно мешает и что нужно. |
| **Skipped** (Retest и др.) | Тест осознанно не выполнялся в этом прогоне (например, фича временно отключена). Уточните у QA-lead, если сомневаетесь. |
| **Untested** | Стартовое состояние: результат ещё не записан. |

Не бойтесь ошибиться: результат можно **изменить или скопировать** кнопками под ним на панели теста (доступно, пока кейс не меняли, и в пределах окна правки проекта — по умолчанию 1 час; для более старых правок просто добавьте новый результат).

## 5. Если тест упал (Failed) — оформляем правильно

Хороший Failed-результат экономит часы разработчикам:

1. **Comment** — по шаблону:
   * Окружение: какая сборка/стенд, устройство/браузер.
   * Шаги воспроизведения: что нажимали (номер шага кейса, если применимо).
   * Фактический результат: что произошло.
   * Ожидаемый результат: что должно быть (из кейса).
2. **Attachments** — скриншот с ошибкой (или лог/видео). Один скриншот стоит абзаца текста.
3. Заведите дефект в баг-трекере проекта (задачи POM1-xxx) и укажите в комментарии ID кейса (например, «дефект POM1-25, кейс AUTH-07») — так дефект и тест найдут друг друга.
4. Дополнительно можно оставить комментарий к самому кейсу (вкладка **Comments** на панели кейса) — например, если считаете, что кейс сформулирован неоднозначно. Сам кейс при этом не редактируйте (см. раздел 7).

После исправления бага на новой сборке просто добавьте новый результат (Passed) — история результатов сохранится, статистика возьмёт последний.

## 6. Test Run — зачем и как (по указанию QA-lead)

**Test Run (прогон)** — это группа тестов, выполняемых на конкретной версии сборки. По умолчанию результаты падают в «TestRun 0» — если QA-lead не дал иных указаний, ничего выбирать не нужно, оставляйте поле Test Run как есть.

Если QA-lead попросил работать в конкретном прогоне:

* при добавлении результата в поле **Test Run** выберите нужный прогон (например, «Сборка 5 — регрессия»);
* свои тесты в прогон можно добавить самому: вкладка **Test Runs** в плане → открыть прогон → **+ Test** → выбрать свои тесты → **Add**;
* создаётся новый прогон кнопкой **+ Test Run** (обычно это делает QA-lead).

Прогресс по статусам смотрите на **Overview** плана: кольцевая диаграмма «Tests Count» показывает, сколько тестов в каком статусе; гистограмма — динамику по дням.

## 7. Правила и полезные мелочи

**Можно и нужно:**

* записывать результаты и комментарии к тестам и кейсам;
* прикладывать вложения (скриншоты) к результатам;
* сохранять свои фильтры («Мои задачи», «Мои P0»);
* пользоваться поиском по Name or ID (например, ввести `COMP-19`);
* фильтровать по меткам: `P0` — красная (критичные, делать первыми), `P1` — оранжевая; метки типов (`Security`, `Access`, `Negative`…) дают готовые срезы;
* перед выполнением кейса заглянуть в **раздел 7.0 плана тестирования** — там легенда: что означают «Админ», «Судья A», базовые тестовые учётки (judge1@example.com…) и правила чтения шагов;
* если в названии кейса стоит пометка «серая зона 3.5.N» — выполнять строго по допущению из **раздела 3.5 плана тестирования** (это зафиксированные договорённости по местам, которые ТЗ не описывает).

**Нельзя / не нужно:**

* **не редактируйте и не удаляйте тест-кейсы и наборы** — они синхронизируются из плана тестирования QA-lead; если в кейсе ошибка — напишите комментарий к кейсу или в чат;
* не удаляйте тесты из планов и не меняйте назначение чужих тестов (массовые операции Move/Assign/Delete в меню **Actions** — только с ведома QA-lead);
* не отмечайте Passed, не выполнив шаги по факту — статистика плана идёт в отчёты приёмки.

**Уведомления:** колокольчик в шапке покажет, когда вам назначили или сняли тест. По умолчанию они выключены — включите в разделе Notifications → Settings.

## 8. Мини-FAQ

| Ситуация | Что делать |
| :-- | :-- |
| «Login Failed» при верном пароле | Вы открываете не тот адрес, который настроен у администратора. Уточните точный URL. |
| Забыли пароль | Напишите администратору (`admin`) — он сбросит. |
| В таблице не вижу своих тестов | FILTER → Assignee → выберите себя; снимите лишние условия фильтра. |
| Не могу изменить результат | Истёк лимит правки (1 час) или кейс обновили — просто добавьте новый результат. |
| Сборка/стенд недоступен | Ставьте Blocked с пояснением, что именно недоступно; сообщите в чат. |
| Кейс непонятен или противоречит ТЗ | Комментарий на вкладке Comments кейса + сообщение QA-lead. |
| Случайно поставил статус чужому тесту | Добавьте новый результат с верным статусом и пояснением; предупредите коллегу. |
| Хочу видеть только P0-задачи | FILTER → Assignee = вы + Label = P0, сохраните фильтр. |

## 9. Шпаргалка: день тестировщика в TestY

```
1. Зашёл → Test Plans & Results → план «Функциональное тестирование — распределение задач»
2. Включил сохранённый фильтр «Мои задачи» (Assignee = я)
3. Открыл тест → прочитал Setup / Scenario / Expected
4. Выполнил шаги на сборке
5. ADD RESULT → статус (Passed/Failed/Blocked) + комментарий + скриншот → CREATE
6. Повторил для следующего теста (P0 — в первую очередь)
7. В конце дня glance на Overview плана — видно вклад каждого и общий прогресс
```

Удачной работы! Вопросы, которых нет здесь — сначала `http://127.0.0.1/docs/` (раздел «Test Plans & Results»), потом — чат команды или QA-lead.
