  (слайды 5–7: SDLC, QA vs QC). Подчеркните: QA-активности начались не после кода, а с анализа ТЗ — это **Shift Left**.

### Блок 1. План тестирования и тест-дизайн (3 мин)

- Открыть [docs/план_тестирования.md](docs/план_тестирования.md:1): цели, границы (Scope), риски,
  правила ТЗ → кейсы. Формулировка: «План **риск-ориентированный** — приоритеты P0–P3 расставлены по
  Риск = Вероятность × Ущерб» (слайды 4, 19–20).
- Показать примеры техник **тест-дизайна** прямо в кейсах (слайды 48–50):
  - **классы эквивалентности и граничные значения** — кейсы оценок 0..10 (FIN-*) и возраст 18+;
  - **негативные тесты** — неверный пароль, дубль ФИО участника, оценка вне диапазона;
  - **таблица решений / матрица прав доступа** — раздел 8 плана (IDOR, подмена роли);
  - **NFR** — раздел 9 (производительность, совместимость, локализация) — это нефункциональное направление (слайд 9);
  - **UAT** — раздел 10: приёмочные сценарии с метриками.
- Показать [docs/распределение_задач.xlsx](docs/распределение_задач.xlsx): 196 функциональных кейсов
  распределены между тремя участниками — это «Планирование» из этапов тестирования (слайд 8).
- Ключевая фраза: «Каждый кейс атомарный и трассируемый: в Description в TestY указан источник —
  раздел и ID плана» (ATOMIC-свойства и трассируемость, слайды 52, 41).

### Блок 2. Флоу TestY — система управления тестированием (4 мин)

TestY поднят локально (`cd testy && docker compose up -d`, интерфейс на http://127.0.0.1).
Показать **жизненный цикл кейса** — это прямой ответ на «как пользоваться testit/testy»:

1. **Проект «Помощник судьи»** → дерево **Test Suites**: наборы 7.1…7.12 (206 функциональных),
   9.x (NFR), раздел 8 (матрица прав), раздел 10 (UAT). Всего 275 кейсов (слайд 44: Suite = группа кейсов).
2. Открыть один **пошаговый кейс**: показать предусловия, шаги с ожидаемым результатом у каждого шага,
   метки приоритета (P0–P3) и типа (`Negative`, `Boundary`, `Security`...) — метки = теги для срезов.
3. **Test Plan** «Функциональное тестирование — распределение задач»: исполнители и сроки назначены
   из xlsx. Показать **прогресс плана** (диаграммы в TestY).
4. **Test Run**: запустить прогон smoke-плана (16 P0-кейсов), проставить результат по одному кейсу:
   Pass, затем один Fail → добавить **комментарий и вложение** (скриншот), связать с дефектом.
5. Показать **статистику прогона** — это основа будущего отчёта о тестировании (слайды 69–70).
6. Упомянуть автоматизацию работы с TMS: импорт 275 кейсов сделан скриптами
   [tools/testy_import/](tools/testy_import/import_test_cases.py:1) через **REST API TestY** —
  «инструмент имеет публичный API, и мы его автоматизировали» (блок «автоматизация всякая»).

Терминология строго по глоссарию из [docs/testy_руководство.md](docs/testy_руководство.md:24) —
Project / Suite / Case / Plan / Run / Result. Прогон smoke — это **дымовое тестирование** (слайд 11).

### Блок 4. Приложение + автотесты (4 мин)

- Поднять приложение (`cd app && docker compose up --build` или локально uvicorn) →
  http://127.0.0.1:8000 — веб-интерфейс, и **Swagger** на `/docs` — показать контракты API
  (лекция про REST/OpenAPI: слайды 15–16, 34).
- Запустить сквозной сценарий: `python scripts/e2e_demo.py` — полный путь «регистрация с
  подтверждением email → соревнование → приглашение → участники → старт → оценки (включая
  офлайн-синхронизацию) → завершение → результаты → отчёты CSV/PNG/PDF». Это **E2E-тест**
  «от А до Я» (слайды 11, 45) и одновременно наглядная демонстрация продукта.
- Автотесты: `pytest --cov=judge_helper --cov-report=term-missing` в [app/tests/](app/tests) —
  211 тестов, **покрытие 97%** при пороге ТЗ 80%. Проговорить:
  - это **модульные и интеграционные уровни** пирамиды тестирования (слайд 12);
  - часть тестов **Data-Driven** — параметризация `@pytest.mark.parametrize` (слайд 61);
  - тесты изолированы (in-memory БД через [app/tests/conftest.py](app/tests/conftest.py:1)) —
    защита от **flaky-тестов** (слайд 20);
  - привязка тестов к группам кейсов плана — **трассируемость** (слайд 52).

### Блок 5. Флоу CI/CD + разбор упавшего теста (5 мин) — главный «вау»-блок

Показать [`.github/workflows/ci.yml`](.github/workflows/ci.yml:1) и живой прогон на GitHub Actions
(есть и параллельный [`.gitlab-ci.yml`](.gitlab-ci.yml) — упомянуть одно предложение).

1. **Схема пайплайна** (открыть вкладку Actions): `lint (ruff)` → `test (Python 3.11/3.12, coverage ≥ 80%,
   junit-отчёт)` → `smoke (/health + веб)` → `docker (сборка → smoke в контейнере → Trivy-скан
   CRITICAL/HIGH → публикация в GHCR)`. Это стадии **Build → Test → Release → Deploy** из лекции про
   DevOps-цикл (слайд 17), а ruff — **статический анализ** (SAST).
2. **Реальный зелёный прогон**: показать, что на push запустилось, все джобы зелёные.
3. **Сценарий падения** (подготовлен заранее, см. раздел 4, пункт 5): push ветки с намеренно
   сломанным тестом → CI красный. Затем «как искать ошибку в логах»:
   - открыть упавшую джобу `test` → прокрутить лог к traceback pytest;
   - показать **как читать вывод**: имя упавшего теста → assert с фактическим/ожидаемым значением →
     путь к файлу и строка;
   - открыть вкладку **Summary**: артефакты `test-reports` (coverage.xml + report.xml/junit) —
     «отчёты можно скачать и изучить локально»;
   - если падение линтера — показать лог `ruff check` (там ошибка видна строкой);
   - лаконичная фраза: «CI сломан → читаем traceback → воспроизводим локально
     `pytest tests/test_xxx.py::test_yyy -v` → фикс → re-push → зелёный».
   - связка с ручным тестированием: дефект из CI заводится в TestY, после фикса — **re-test**
     (перетестирование исправленного, слайд 11).
4. **Финал флоу — деплой одной командой**: после публикации образа в GHCR на ноутбуке
   выполняется `docker compose -f docker-compose.deploy.yml up -d` → скачивается свежий образ,
   приложение поднимается на http://127.0.0.1:8000, **миграции применяются автоматически при
   старте** (`create_app` → `create_all` + `run_simple_migrations`). Фраза: «только что
   запушенный код уже работает локально — непрерывная доставка в действии».
5. Показать **Security tab** (Code scanning alerts от Trivy) и [`.github/dependabot.yml`](.github/dependabot.yml:1) —
   «сканирование образа и зависимостей — тестирование безопасности в пайплайне» (слайды 46, 72–75).

- Фраза-вердикт: «По критериям выхода — Blocker/Critical = 0, покрытие ≥ 80%, критерии приёмки UAT
  выполнены — рекомендуем релиз: **Go**» (Exit Criteria, слайд 19).

  тестировщика — «мы не заводим в работу всё подряд, найденное сортируем».
- Завершить перечень документации проекта одним экраном README: ТЗ → план тестирования → кейсы

  баг-репорты → итоговый отчёт. Фраза: «Документация по всем стадиям цикла тестирования —
  от требований до closure» (слайды 8, 13, 34).

## 5. Вероятные вопросы комиссии и короткие ответы

- **«Почему покрытие 97%, а порог в CI 80%?»** — Порог — минимальный контракт ТЗ (fail-fast защита от
  деградации); фактическое покрытие выше, но порог установлен по достижимому и осмысленному уровню,
  а не «100% ради цифры» (слайд 58: автоматизация не ради покрытия всего).
- **«Почему PyTest, а не Playwright/Selenium?»** — Продукт — API + простой веб-интерфейс; по пирамиде
  (слайд 60) основа — unit/API-тесты (быстрые, стабильные); UI-слой минимален, E2E закрыт скриптом.
  Playwright — дефолт для веб-UI, но здесь узкое место не UI.
- **«Что такое flaky-тесты и как с ними боретесь?»** — Слайд 20: изоляция (своя БД на тест),
  детерминированные данные, фиксированные значения времени; никаких sleep-ов и порядка выполнения.
- **«Где у вас TDD/BDD?»** — Тесты создавались параллельно с кодом (shift-left), Gherkin не использовали:
  команда маленькая, заказчик читает тест-кейсы в TestY — ту же роль валидации требований выполняет
  трассировка кейс↔тест (слайд 18: TDD для unit, BDD для приёмочного уровня; у нас приёмку ведёт TestY).
- **«Как связаны автотесты и ручные кейсы?»** — Один источник: план тестирования; кейсы заведены в TestY,
  автотесты привязаны к тем же группам; регресс-часть — авто, новое/исследовательское — вручную (слайд 58).
- **«Что делает Trivy и зачем?»** — Сканер уязвимостей Docker-образа и конфигураций (слайд 75:
  автоматизация для сканирования конфигураций); CRITICAL/HIGH попадают в GitHub Security tab.
- **«Как вы искали причину падения CI?»** — Раздел 2, блок 5: traceback pytest в логе → воспроизведение
  локально с `-v` → фикс → re-push → re-test кейса в TestY.
